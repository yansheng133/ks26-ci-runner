# ks26 約束包 —— 讓任何 AI 都寫得出可上線的東西

## 這一包在主張什麼

要讓 agent 產出「能上線」的東西，直覺的做法是把提示詞寫得更長、更詳細。這條路不可靠：
提示詞只能**提高機率**，不能**保證結果**，而且換一個模型、換一天，結果就不一樣。

這一包走的是另一條路：

```
需求（要什麼）  ＋  約束（怎樣才算做對）  →  agent 產出  →  自動驗證  →  沒過就退回重做
                                                              ↑                      │
                                                              └──────────────────────┘
```

**關鍵不是提示詞，是最後那一道閘門。** 只要驗證是機器做的、而且不過就退回，
那麼換成任何一個 agent，交出來的東西都會落在同一條線以上——因為它非過不可。

這正是人在 AI 時代真正的工作：**不是逐行讀碼，是決定哪些約束該存在，然後為放行負責。**

## 檔案

| 檔案 | 誰讀 | 內容 |
|---|---|---|
| `REQUEST.md` | agent | 那「一句需求」 |
| `hard-constraints.md` | 人 | 十一條硬性限制，每條對應一個檢查代號 |
| `AGENTS.md` | agent | 產出規則與交件條件（模型無關） |
| `verify.sh` | 機器 | 二十四項檢查。全過才算交件 |
| `examples/good/` | 人 | 全數通過的參考產出 |
| `examples/violations/` | 人 | 刻意違反四條的版本，用來看「沒過長什麼樣」 |

## 怎麼用

```bash
# 1. 把 REQUEST.md 與 hard-constraints.md 交給你手上的 agent，並要求它讀 AGENTS.md
# 2. agent 產出之後，讓它自己跑：
./verify.sh

# 3. 沒全過就修，修到全過。全過才送審。
```

驗證器本身零安裝：本機有 `yq` 就直接用，沒有的話它會自動改用容器跑同一套檢查
（`docker` / `podman` / `nerdctl` 擇一即可）。

回傳值：全過 `0`，有任何一條沒過 `1`——所以它也可以直接掛進 CI。

## 兩個例子怎麼看

`examples/good` 全數通過。`examples/violations` 刻意違反了四條，跑起來會看到：

- **C04** 標籤是 `latest`、`imagePullPolicy` 沒明寫
- **C05** 整段 `resources` 不存在
- **C06** `privileged: true`
- **C10** `APP_OWNER` 還是 `TODO-填你的團隊`

這四條是最常見、也最容易被放過去的。它們的共同點是：**都寫得成一條規則，
而且違反時不用把服務跑起來就看得見**——所以人有機會在放行之前真的看懂自己在放行什麼。

## 回去之後改哪裡

改 `hard-constraints.md` 和 `verify.sh`，**成對地改**。
表上加一條，驗證器就要加一個檢查；加不出檢查的那一條，先別加進表裡——
那表示它還沒被想清楚，放進去只會變成沒人遵守的條文。
